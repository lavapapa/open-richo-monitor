# 当前商品接口的请求签名

说明依据本项目现有 `crates/core/src/ricoh_api.rs` 的实现，以及本轮真实商品响应。这里描述应用实际发送的请求；服务端具体的时间窗口、随机数去重规则与验签实现未公开，本文不推测那些规则。

## 一、请求构成

应用发送 GET 到 `https://shop.ricn-mall.com/app-api/product/detail`，参数是 `productId=65&skuId=`。浏览器地址栏访问相同 URL 时会收到“请求签名缺失”，因为普通页面跳转没有应用附加的三个请求头。

应用先取 Unix 时间戳，单位毫秒；再生成六个随机字节，将它们编码成十六进制并与时间戳组成 nonce。nonce 是每次请求的随机标记。然后构造固定顺序的签名原文：

```text
GET
/product/detail
productId=65&skuId=

{timestamp}
{nonce}
```

签名中的路径为 `/product/detail`，实际访问路径保留 `/app-api/product/detail`。两者按既有接口协议分别使用。查询参数包含空的 skuId，参数顺序、换行和空行都会影响签名结果。

## 二、计算与发送

现有实现将协议内置签名字符串、一个换行、上述原文拼接，计算 SHA-256 摘要并输出小写十六进制。这里调用的是普通 SHA-256，代码没有使用 HMAC。随后将时间戳、nonce、摘要分别放入 `X-Request-Timestamp`、`X-Request-Nonce`、`X-Request-Sign` 三个请求头。

这条公开商品读取路径不依赖个人 Cookie 或 Bearer 登录令牌。签名字符串已经存在于应用的接口实现中，本轮沿用该机制，没有增加新的签名算法。库存检查、手动添加及扫描复用该签名客户端和请求调度。

## 三、错误区分

缺少签名、HTTP 身份/访问拒绝、业务响应解析失败属于接口响应层的信号。连接超时发生在请求尚未得到响应的网络阶段，调整签名算法不能据此解决连接问题。本轮接口验证与随后原生监控均成功，但早期一次直连超时没有足够证据归因到签名、DNS、TLS 或服务端。

当前实现保留底层错误链，界面通过红色“检查失败”打开原始诊断。定位网络问题应结合错误链、连接耗时及当时的代理配置判断，避免将不同阶段的错误混在一起。
