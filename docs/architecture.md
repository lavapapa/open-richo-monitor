# 三层设计

应用使用前端、命令适配、监控核心三层。桌面和 CLI 共用核心用例与持久化规则，界面操作通过命令获得结果与快照。行为契约见[应用契约](app-contract.md)，本文件描述当前实现职责。

## 一、分工

三个层面分别拥有展示、入口适配和业务状态，按同一方向调用，业务结果通过快照和事件返回界面。

### 1.1 前端

`apps/desktop/src/routes/+page.svelte` 负责导航、表单草稿、筛选、虚拟表格、弹窗和操作反馈。`src/lib/desktop-api.ts` 定义类型并封装 Tauri invoke 与状态订阅。前端显示核心提供的检查次数、观察结果和扫描进度；切页、隐藏窗口、卸载组件不会结束核心任务。

外观选择保存在 WebView 的界面偏好中，`theme-init.js` 在首屏加载时应用选择，`theme.css` 通过系统媒体查询实时切换配色。主题、表格筛选与未保存表单草稿属于前端状态，不写入监控配置。

### 1.2 命令适配

`apps/desktop/src-tauri/src/desktop_backend.rs` 将桌面命令转换为 `MonitorApp` 用例调用，提供成功结果、错误和带平台信息的快照。原生文件对话框、登录启动、系统通知权限、日志目录和更新由这一层处理。`test_system_notification` 在一次命令内完成权限查询、必要的申请、缓存更新与发送，前端按返回结果展示反馈。

应用启动时，`src-tauri/src/lib.rs` 将实际数据目录下的 `images` 目录加入本地图片读取范围，主窗口、商品详情与突出提醒共用这一范围。调试版指定独立数据目录时，图片读取范围随该目录调整。

`src-tauri/src/lib.rs` 管理应用生命周期、后台工作任务、托盘与状态转发。关闭窗口保持后台运行，主窗口打开入口共用显示、解除最小化和聚焦；macOS 重新打开事件恢复主窗口，退出应用等待核心收尾；后台任务的退出或 panic 发布故障状态并阻止继续提交运行操作。系统通知独立消费核心待投递记录，提交回调不会阻塞快照转发。系统通知在 `desktop_notifications.rs` 按目标平台调用原生接口，静态代理由 `notification_proxy.rs` 读取，通知模块位置由 `notification_runtime_path.rs` 按调试或安装布局定位。平台构建配置将相应可执行文件打入安装包。CLI 在 `crates/cli/src/main.rs` 将参数转换为相同核心用例。CLI 命令实例通过共享数据库提交运行意愿和配置，运行实例读取并应用变更。

### 1.3 核心

`crates/core/src/app.rs` 的 `MonitorApp` 是业务入口，拥有配置、商品、渠道、代理、扫描和运行操作，以及 `snapshot`、`query_messages`、`run_loop` 与 `shutdown`。核心依赖 Rust 网络、调度与存储模块，独立于 Tauri、Svelte 和浏览器。`scheduler.rs` 管理请求线路、随机间隔、失败等待及共享请求闸门。`storage/runtime_storage.rs` 保存请求水位与健康进度，`storage/notification_outbox.rs` 保存待投递记录及确认结果，`storage/history_storage.rs` 执行筛选和游标分页；这些事务与资源范围遵守应用契约。通知模块处理提供商请求与结果。

调度层根据核心配置选择每出口一条列表任务或每商品一条详情线路。列表分页先构成有界完整轮次，再把出现与缺席结果交给相同的观察归并和存储事务；命令层保存方案并返回快照，前端呈现方案选择与库存是否提供。出口健康按列表轮次归并一次，商品检查计数仍分别累计。解析错误不会计作出口传输失败。

### 1.4 平台适配

macOS 与 Windows 使用同一套 Core、Svelte 界面和 Bun 通知脚本。Rust 的 `cfg(target_os)` 将系统通知、代理读取、登录启动和突出提醒交给对应系统 API；目标 Tauri 配置选择运行时二进制、资源和安装程序。功能修复与业务测试进入共同源码，平台验收分别运行。平台 Git 分支会让同一业务修改产生两份维护工作，当前工程沿用框架适配边界。

桌面后台运行由登录用户的应用进程承担：关窗保留托盘与任务，显式退出等待核心及通知子进程收尾，登录启动由系统用户启动项恢复。无人登录运行的 Windows 系统服务需要独立的宿主和状态边界，当前桌面范围不包含这项能力。突出提醒在启动时预加载隐藏页面，复用窗口并通过 Tauri Channel 直接传递商品；Core 事务唤醒专用消费者，必要页面内容提交后交由原生主线程显示，图片异步加载。具体队列与显示确认规则见[引导与突出提醒契约](onboarding-alert-core.md)。原生通知采用 macOS UserNotifications 与 Windows WinRT；通知系统代理使用 macOS scutil 与 Windows 当前用户 WinHTTP 配置；Windows 按实际 HTTP、HTTPS 与 WebSocket 目标解析 PAC、WPAD、静态代理和绕过规则。解析在独立短命子进程执行并有界取消，运行程序按目标短时缓存结果；显式 PAC 失败返回错误。macOS 无法处理的自动代理配置返回明确结果。

## 二、时序

命令入口合理划分后，执行中的请求仍可能与后续操作交错。旧任务取消和结果提交约束由核心统一执行，桌面与 CLI 遵守相同规则。

### 2.1 交互与反馈

用户提交操作后，前端等待命令结果并刷新快照。命令层将业务输入交给核心；核心提交配置或运行意愿，运行循环应用变化并发布快照。前端在窗口重新获得焦点时重新读取状态。按钮的等待状态用于防止重复交互，核心仍独立保证业务结果一致性。

增选商品启动对应线路，已有商品保留在途请求和客户端。调整请求间隔与失败提醒阈值热更新线路；调整计划取消旧计划任务并重新评估时段；网络出口变化重建对应网络运行环境。具体行为以应用契约及生命周期回归测试为准。

### 2.2 写入与取消

商品启停、运行暂停和配置导入等操作在存储事务中结束相关商品轮次。检查结果在同一写事务中核对轮次、启用状态和运行意愿，然后记录检查次数、健康状态与观察结果。事务开始后再发生的控制操作按数据库写入顺序执行；事务前已结束的轮次失去提交资格。

扫描使用扫描标识绑定任务及检查点，启动、暂停、取消和提交通过对应事务处理。旧扫描结果无法更新后续扫描，扫描期间移除的商品在该轮保持移除。运行实例读取持久化检查点以响应其他命令实例。

## 三、验收

测试分别覆盖界面交互、命令协议和核心时序，原生验收补充 WebView、操作系统集成与真实网络链路。自动通过与原生通过分别记录。

前端测试检查操作等待、失败恢复、快照展示、主题持久化和命令调用。桌面后端测试检查权限分支及退出时序。核心集成测试使用可控制的延迟响应复现增选、取消再勾选、暂停恢复、导入及扫描取消等交错操作。平台行为通过实际 App 验收，具体场景见测试规范。

这三个职责边界共同保持状态可解释：界面表达用户意图，命令适配系统入口，核心维护业务时序与持久化事实。
